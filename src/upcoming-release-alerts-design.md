# Upcoming-app release alert design (draft, not deployed)

The standalone preview is `upcoming/index.html` with six-language UI; no registration is active. The existing production catalog and download buttons are unchanged. Do not enable publishing until the release-alert service is verified, and remove noindex only when the owner approves publication.

## Free-only backend requirements
- Dedicated separate Workers Free project and dedicated D1 subscription database; no R2, paid Workers, paid Zero Trust, billing activation, shared dashboard DB or administrative IARC/console fields.
- Browser web push only after explicit app-by-app opt-in with explanation and a visible unsubscribe control. No permission prompt before clicking. Support detection and truthful error/unsupported notices. No email or identity collection. Retain minimal push endpoint/key material and chosen app IDs, plus language, consent date and expiration. Never expose endpoint or keys to public responses/logs/repository. Service worker limited to public homepage scope; notification click can open verified public app URL only.
- Strict endpoint validation (known push-service HTTPS host allowlist, no redirects, bounded size); origin restrictions and request caps, write limits, idempotent registration/unregister and deletion for expired subscriptions. Store a hashed opaque per-browser token for unsubscribe authentication, not the raw token.
- VAPID private key and release-administrator authentication only as Worker secrets. No secret in frontend, public GitHub, or screenshots.
- Release registry is app slug -> verified public store URL and observed release publication timestamp, not production approval or staged draft. Only update after authorized read-only verification of actual production publication; never send for development or testing. Release trigger must require owner authentication and reject URL outside the approved Google Play/App Store domains.
- D1 unique (subscription, app, release) dispatch key, bounded daily work, at-most-once dispatch semantics (uncertain outcome not automatically retried), expired/invalid endpoint removal. Stop gracefully when free quota is reached. No silent fallback to paid services.
- Use maintained Web Push implementation and test cryptographic compatibility, subscribe/unsubscribe permission and delivery on Chrome/Android, plus iOS installed Home Screen web app requirement and desktop/mobile responsiveness. Tests must use local or synthetic endpoints, never real subscribers, and verify no push before release.
- For a public release, switch each app card from "Coming soon" to a verified production download button and keep existing homepage links. Add optional explicit notification setting after the backend is deployed and tested. Never publish a fake or inactive registration button as a working feature.

## Evidence & limitations
The sixteen brief descriptions were cross-checked against app source READMEs. Eight utility launcher icons are their actual app PNGs. The remaining eight character app icons have not been copied because their real source PNGs exceed connector content limits; initials are intentional placeholders and not app icons. No private app metadata or test links are included. No scheduling, registration, Cloudflare resource creation, production deployment or notification dispatch was performed.
